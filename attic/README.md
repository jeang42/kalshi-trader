# attic/ — retired code, kept for reference

**Nothing in here runs, is imported by live code, is linted, type-checked or
tested by CI.** Every module was moved out of the repository root on
2026-08-17 (P2 / R-17) because its thesis was measured dead, its only
consumer was retired, or it was scratch work — and until then it sat next to
the live arms with no structural signal separating the two. The findings the
code produced are recorded in `docs/failed-experiments.md` and
`docs/edge-research-log.md`; the code is here so those findings stay
reproducible, not so it gets re-run casually.

`git log --follow attic/<file>` shows each file's full history at its old
path.

## Running something from here (if you must)

Modules still `import` the live root modules (`kalshi_client`, `book_archive`,
…) and, for the scratch cluster, each other. Run from the repo root with both
on the path:

```bash
PYTHONPATH=.:attic .venv/bin/python attic/<module>.py [args]
PYTHONPATH=.:attic .venv/bin/pytest --no-cov -p no:cacheprovider attic/tests/<test>.py
```

> **⚠ Path drift since 2026-08-24 (R-24 Phase A):** the live root modules these
> files import (`kalshi_client`, `book_archive`, `portfolio`, `calibration`,
> `execution`, `provider`, …) moved under `pm/` (`pm/venue/`, `pm/archive/`,
> `pm/ledger/`, `pm/trading/`). Attic code was deliberately NOT rewritten — it
> is retired, and its findings are already recorded in the docs. To actually
> re-run something from here, either edit its imports to the `pm.` paths or add
> a small sys.path shim; expect further drift as later phases move more of the
> root. The findings do not depend on this code re-running.

`attic/tests/` holds the tests that moved with their modules. They are NOT
collected by `pytest` (`norecursedirs` excludes `attic`), and they run without
the root `conftest.py`'s isolation fixtures unless invoked as above from the
repo root — so treat them as documentation of intended behaviour, not as a
gate. Several were passing on the day they moved; nothing guarantees they
still do.

`attic/deploy/systemd/` holds the unit files of the retired services. They
were **uninstalled** from `~/.config/systemd/user` on 2026-08-17 (all were
`disabled`/`inactive`; the one enabled timer, `consensus-calibration-check`,
was a one-shot that had already fired 2026-06-05). To resurrect one, copy it
back, fix its `ExecStart` path, `daemon-reload`, and read the post-mortem
first.

## To bring something back to the root

1. `git mv attic/x.py x.py` (and its test back to `tests/`).
2. Restore its row to the file map in `docs/file-map.md` — a line or two only; the
   verbatim row below is the long form and belongs in `docs/module-notes.md`,
   linked from the row as ↳ (`docs/file-map.md` was split on 2026-08-23, R-25).
3. Add it to `--cov=` in `pyproject.toml` if it transacts.
4. Re-read the failed-experiments entry that retired it, and say in the
   commit message why the verdict no longer holds.

The headline numbers below (+11.8% ROI, 86% win by event, "PROMISING") are the

### `fade_retail_backtest.py`

**De-correlated, cost-aware backtest of the FIRST +EV EDGE (2026-06-30).** Favorite-longshot bias in NON-sport/crypto RETAIL markets (primaries/awards/music — arbitrageur-light). At a 72h lead, YES 0.15–0.55 resolves YES far less than its price (gap −8 to −19pp). Fade = BUY NO, hold to resolution. Groups by EVENT (ticker minus last `-member` segment) since one-winner fields' members are correlated → the honest independent observation. Result: 21 independent events, **+11.8% ROI net of a 4¢ spread haircut, 86% win by event, top-1-event share 15% (NOT fat-tailed)**; Entertainment +34% / Elections +20% / Politics −6%. Works offline from a `get_market_calibration_data` CSV. See `[[project_retail_longshot_fade]]`. CLI: `python fade_retail_backtest.py --csv <cal.csv>`.

### `fade_retail_longshot.py` + `~/.config/systemd/user/fade-retail.service`

**Forward paper arm for the retail-longshot fade** (clean out-of-sample validation of `fade_retail_backtest`). Discovers via **`get_markets_closing_within(MAX_DAYS)` — close-time, NOT the volume feed** (retail primaries/awards/mention fields don't surface in volume-ordered `get_markets`, same gotcha as MLB/econ); `is_retail_series` excludes sport (incl `KXWC` World Cup), crypto, AND scheduled macro (CPI/GDP/Fed/central-bank — efficient, not the behavioral corner). Takes retail longshots (YES ∈ [0.12,0.45], vol>500, closes in [2,45]d — velocity horizon, soonest-resolving filled first), **buys NO paper** at (1−yes_bid), logs NET P&L (NO pays $1 if the thing didn't happen). **Live-execution CANARY** (`FADE_CANARY_ENABLED`, **default off/DORMANT**; profile `agentic_fade_retail`): when enabled AND profile ∈ `LIVE_TRADING_PROFILES` AND live gates pass, each new fade also places ONE 1-contract REAL buy-NO through `execution.LiveBroker` (pre-flight caps + emergency-stop) to validate NO orders FILL on thin retail books; records `live_order_id`/`live_status`, ≤`FADE_CANARY_MAX_PER_CYCLE` (5)/cycle; triple-gated → any missing gate = no-op. **Early-exit take-profit** (`FADE_TP_FRACTION`, **default 0.0 = DISABLED**): sells an open NO once it captured ≥N% of its move. Built as a velocity lever but `fade_early_exit_backtest.py` FALSIFIED it — corrections happen late (~4.7 of 6 hold-days) so a 0.6 TP roughly HALVED ROI (17.3%→7.9%) to save ~1 day; hold-to-resolution wins on return AND is fast enough (~6d, velocity via breadth). Code kept + env-tunable, off by default. `--stats` splits P&L by exit_reason (resolution vs take_profit) w/ avg hold days. **Prop-overround targeting (sharpest sub-edge):** groups by EVENT, computes each field's `overround` = Σ mid of plausible (0.08–0.65) members; strongly-overround fields (Σ≥1.6 — "which of N plausible things happens" props like Drake features / Met Gala where retail overprices EACH candidate but only 1–2 hit) get a wider per-event cap (6 vs 2) to fade the whole field. Positions **tagged by market-type** (`classify_mtype`: say_mention / feature_attend / win_award / election / music) + strategy (overround vs broad) so `--stats` shows OOS P&L per type (the backtest's +60% on features was really ~2 correlated events — this tells us which cut holds up across MANY independent events). ### `pm/arms/back_nearclose.py` + `~/.config/systemd/user/back-nearclose.service`

**Back-nearclose — near-close FAVORITE-BACK paper arm (buy YES 0.90–0.98)**, the mirror of `fade_nearclose` and the other half of one bias (2026-08-02). Re-mining the near-close panel across band × class × **SIDE** (the side sweep the 07-09 mine never ran — it tested buy-NO only) showed backing near-certain favourites is +EV in continuous-underlying classes and NEGATIVE in the one class where fading longshots works: crypto +1.58¢/ct (n=670), commodity +2.62¢, finance +0.98¢, **discrete −3.37¢ ← never trade**. *Mechanism*: same favourite-longshot bias harvested from the expensive side — retail lottery demand bids up the cheap side so the other side gets cheap, and the near-settle Gaussian drift that made our weather/commodity longshot FADES lose is exactly what pays the favourite buyer. Discrete markets have no such drift, so the sign flips. The two arms hold different tickers (0.94 vs 0.15) so they compose rather than overlap. **Verified at build time, spec corrected twice**: (1) the 07-30 headline +2.31¢/ct does NOT hold at more data — de-duplicated per `(asset, close-hour)` it is **+1.15¢/ct, 97% win, n=757, thirds +1.19/+0.95/+1.30** (all positive; de-dup slightly IMPROVED it); (2) the weather cell is **DROPPED** (decays +6.51/+0.37/−1.49¢ — most recent third negative). **Discovery is TWO-PASS** (`FAR_BAND_LEAD_HOURS`): a bare `get_markets_closing_within(2h)` hits the 1000-row cap and, being closing-soonest-first, silently truncated us to **8 minutes of lead** (75% of rows; max 68 min) — the arm would never have seen most of its own window. Far band (`min_days`) + near band, unioned. *Same bug exists in `fade_nearclose`* (median hold 38 min, not 2h) — left alone deliberately, since its edge was validated on its realized fills at that lead. Trades ALL leads: filtering to `lead≥1.0h` has a higher mean (+2.70¢) but a NEGATIVE middle third (n=131) vs all-leads positive in every third — declined as a cherry-pick. **2026-08-06 first read (n=263): the whole loss was ONE underlying** — WTI n=78 −$— (−6.43¢/ct, 88% win) + NASDAQ n=5 −$—, vs **everything else n=180 +$— (+2.30¢/ct, 97% win)**. Cause: a population mismatch — the panel was 88% crypto (commodity a thin n=37) but the live 2h window surfaces mostly commodity settles, so the arm ran 58% commodity / 31% WTI, trading a cell the research barely measured. `EXCLUDE_UNDERLYINGS = {WTI, NASDAQ}` (held to the replication test first: WTI negative in 2 of 3 thirds −6.34/−13.90/+0.95¢ vs the rest positive in all 3 +3.57/+1.77/+1.56¢, and 88% vs 97% win = different population; **caveat: WTI's newest third is POSITIVE, so this is a hypothesis under test — revisit if it turns**). Replay over the real record: −$— → **+$—, +2.30¢/ct, 97% win**. Buys YES at ask, mid ∈ [0.90,0.98) and **ask ≤ 0.97** (EV arithmetic: at a ~3% loss rate, 0.985 needs >99.4% win), uniform $— 1 per event AND per `(asset, close-hour)`, holds to settlement, resolves off raw `status=="finalized"` + `result`. **Risk shape: ~97% win ~+1¢/ct, ~3% lose the whole ~94¢ entry (+11¢ per win vs −$— per loss at $—) — judge on mean P&L per cluster, NEVER win rate.** PAPER ONLY (imports neither `kalshi_orders` nor `execution`). Pure `classify`/`in_band`/`backable` doctested; 15 unit tests. SQLite `data/shared/back_nearclose.sqlite` (env `BACK_NEARCLOSE_DB`, resolved lazily — no import-time constant). systemd `--loop --interval 900`. CLI: `python back_nearclose.py [--stats]`.
